# FretFormula — спецификация реализации для Codex Astra

Статус: обязательная продуктовая и техническая спецификация.

Целевой исполнитель: основной агент Codex на модели `gpt-5.6-sol` с reasoning
`medium`. Основной агент обязан использовать субагентов для подходящих простых операций
и выбирать для них минимально достаточную модель и reasoning, обеспечивающие
качественный результат без лишнего расхода токенов.

Документ дополняет, но не заменяет:

- `C:\dev\Godot\games\AGENTS.md` — общие правила, пути Godot и глобальный MCP;
- `AGENTS.md` — правила проекта FretFormula;
- `docs/DEVELOPMENT_PLAN.md` — существующую дорожную карту;
- `README.md` — фактическое состояние и команды запуска.

При конфликте действуют `AGENTS.md` согласно их области видимости, затем эта
спецификация. Существующий проект является частично реализованным каркасом, а
не пустой заготовкой: перед изменениями нужно проверить актуальный код и не
перезаписывать уже корректные решения без необходимости.

## 1. Видение продукта

FretFormula — автономное учебное приложение для осмысленного изучения гитарного
грифа. Пользователь выбирает тонику, гамму или лад и сразу видит все входящие
ноты на грифе, их ступени, точные октавы и взаимосвязь с позициями и системой
CAGED. Любую видимую ноту можно сыграть касанием; несколько одновременных
касаний должны звучать полифонически как интервал или аккорд.

Приложение должно быть полезно одновременно для трёх сценариев:

1. запоминание расположения нот и ступеней по всему грифу;
2. изучение гамм, ладов, позиций и связей CAGED;
3. слуховая проверка выбранных нот, интервалов и созвучий.

Технологическая основа: Godot 4.x, GDScript, без обязательного сетевого
соединения. Текущий проект настроен на Godot 4.7 и `GL Compatibility`; менять
версию или рендерер можно только при подтверждённой технической причине.

## 2. Цели MVP

MVP считается полезным законченным первым слоем, а не статичным макетом. Он
должен обеспечивать:

- выбор любой из 12 тоник;
- универсальный каталог гамм и ладов, загружаемый из данных;
- мажорную и минорную пентатоники;
- мажорную гамму;
- натуральный, гармонический и мелодический минор;
- минорную блюзовую гамму;
- семь модальных ладов мажорной гаммы;
- отображение подходящих нот на всём настроенном диапазоне грифа;
- режимы подписей **Ноты**, **Ступени**, **Оба**;
- визуально и семантически отдельное выделение тоники;
- три равноправных режима области: **Весь гриф**, **Позиции**, **CAGED**;
- CAGED уже в MVP, включая пять форм C/A/G/E/D;
- корректную высоту ноты для каждой пары «струна + лад»;
- воспроизведение точной высоты при нажатии на видимую ноту;
- независимые multitouch-контакты и не менее 6 слышимых одновременных голосов;
- стандартный строй E2–A2–D3–G3–B3–E4 по умолчанию;
- доменную архитектуру без предположения о фиксированных шести струнах;
- адаптивный интерфейс для desktop, tablet и mobile;
- основу для последующего добавления аккордов, арпеджио, тренажёра и
  локальной статистики без переписывания музыкального ядра.

## 3. Нецели MVP

В первый релиз не входят:

- аккаунты, облачная синхронизация, социальные функции и рейтинги;
- распознавание сыгранного звука с микрофона;
- тюнер, DAW, нотный редактор и запись аудио;
- реалистичная физическая модель конкретной гитары;
- сетевой каталог пользовательских гамм;
- полная система аккордов, арпеджио, интервальных упражнений и статистики —
  для них нужны расширяемые интерфейсы, но не полный UI MVP;
- обязательная поддержка нестандартных строев в CAGED. Для несовместимого
  строя режим должен честно сообщать об ограничении, а не показывать неверную
  форму;
- iOS-публикация, если нет доступного окружения подписи и реального устройства.

## 4. Пользовательские сценарии

### 4.1 Исследование гаммы

Пользователь выбирает тонику C и дорийский лад. Гриф немедленно показывает
только входящие ноты. Переключение «Ноты → Ступени → Оба» не меняет набор
позиций, а только подписи. Все C выделены как тоники.

### 4.2 Изучение позиции

Пользователь включает «Позиции», выбирает позицию из доступного списка и видит
её границу, основной диапазон и перекрытие с соседними позициями. Ноты вне
позиции либо скрыты, либо приглушены согласно единой настройке представления.

### 4.3 CAGED

Пользователь включает CAGED, выбирает форму E и тонику G. Приложение показывает
транспонированную форму, корни, аккордовые тона и остальные ступени гаммы в
окрестности формы. Переход через 12-й лад сохраняет октавную эквивалентность.

### 4.4 Игра касаниями

Пользователь удерживает три ноты тремя пальцами. Все три звучат одновременно.
Отпускание одного пальца останавливает только принадлежащий ему голос. После
сворачивания приложения не остаётся зависших нот.

## 5. UX и адаптивный интерфейс

### 5.1 Информационная иерархия

Главным интерактивным объектом всегда остаётся гриф. Элементы управления не
должны вытеснять его с экрана.

1. Верхняя панель: название/компактный логотип, тоника, гамма или лад, режим
   подписей, настройки.
2. Панель контекста: весь гриф, позиции, CAGED; при необходимости — выбор
   позиции либо формы.
3. Гриф: струны, лады, маркеры, ноты, граница выбранной формы/позиции.
4. Нижняя строка или всплывающая карточка: легенда и данные активной позиции.

Визуальный референс `docs/reference/fret_formula_ui_reference.png` задаёт
направление, но не является пиксель-в-пиксель контрактом.

### 5.2 Состояния и управление

- Выбор тоники и гаммы должен быть доступен максимум за два действия.
- Текущий выбор сохраняется между запусками после появления `SettingsStore`.
- Нажатая нота получает немедленную визуальную реакцию независимо от аудио.
- Карточка позиции показывает: имя с октавой, ступень, номер струны, лад,
  MIDI-номер и частоту.
- Открытая струна отображается как лад 0 и участвует в hit-testing наравне с
  остальными позициями.
- Для desktop мышь эмулирует один независимый указатель; клавиатурные shortcuts
  допустимы как дополнение, но не как единственный способ управления.
- Для mobile основной режим — landscape; portrait должен либо оставаться
  функциональным с прокруткой, либо показывать явное предложение повернуть
  устройство без потери состояния.

### 5.3 Адаптивность

Поддержать как минимум контрольные размеры:

- mobile landscape: 640×360 и 800×360 logical pixels;
- tablet: 1024×600 и 1280×800;
- desktop: 1280×720, 1440×900 и 1920×1080;
- произвольное изменение размера desktop-окна без рассинхронизации рисунка и
  зон нажатия.

Компактная mobile-панель может сворачивать подписи и переносить вторичные
настройки в popup. Минимальная интерактивная область — ориентировочно 44×44
logical pixels, если это не делает музыкальные позиции геометрически ложными;
для тесного грифа допускается увеличение hit-area без увеличения маркера.

### 5.4 Доступность

- Цвет не является единственным признаком тоники, ступени или нажатия.
- Тоника отличается цветом, контуром/формой и подписью `1` в режимах ступеней.
- Контраст текста и маркеров проверяется на выбранной палитре.
- Шрифт и маркеры масштабируются; критические подписи не должны обрезаться.
- Для диезов и бемолей должна быть настройка написания, а не смена высоты.
- Подготовить RU/EN-ключи интерфейса; строки доменной модели не зашивать в UI.

## 7. Модель данных

### 7.1 Основные типы

`Pitch`

- `midi_note: int` — абсолютная высота;
- вычисляемые `pitch_class: int` в диапазоне 0…11 и `octave: int`;
- допустимый практический диапазон проверяется аудиодвижком, но доменная
  формула остаётся общей.

`Interval`

- `semitones: int` в диапазоне 0…11;
- каноническая ступень (`1`, `b2`, `2`, `b3`, …);
- отображаемое имя не определяет числовую высоту.

`ScaleDefinition`

- стабильный `id`;
- локализуемые `name_key` и `category`;
- упорядоченный массив уникальных интервалов;
- `0` обязателен;
- метаданные семейства/режима и порядок показа.

`Tuning`

- стабильный `id`, `name_key`;
- `open_string_midi`, от самой низкой по высоте струны к самой высокой;
- произвольное положительное количество струн;
- опциональные рекомендуемые подписи.

`FretPosition`

- `string_index` — индекс в `open_string_midi`, не визуальный номер строки;
- `fret` — 0…`fret_count`;
- `midi_note = open_string_midi[string_index] + fret`;
- `pitch_class = posmod(midi_note, 12)`;
- `octave = floor(midi_note / 12) - 1`;
- `interval_from_tonic = posmod(pitch_class - tonic_pitch_class, 12)`;
- опциональные `degree_label`, `is_tonic`, `is_chord_tone`, `region_ids`.

`FretboardViewModel` содержит рассчитанные позиции, геометрию и визуальные
роли, но не Godot-ноды. Его можно тестировать headless.

### 7.2 Внешние данные

Гаммы, лады, строи, позиции и CAGED-формы должны находиться в JSON либо в
кастомных Godot `Resource`, но не в константах UI-кода. Для MVP предпочтителен
валидируемый JSON с версией схемы:

```json
{
  "schema_version": 1,
  "scales": [
    {
      "id": "minor_pentatonic",
      "name_key": "scale.minor_pentatonic",
      "category": "pentatonic",
      "intervals": [0, 3, 5, 7, 10]
    }
  ]
}
```

Loader должен возвращать понятные ошибки с именем файла и `id` записи.
Невалидная пользовательская запись не должна повреждать встроенный каталог.
Минимальная валидация: версия схемы, уникальный `id`, обязательный интервал 0,
целые интервалы 0…11, отсутствие дублей, непустой строй и допустимые MIDI.

## 8. Музыкальная теория и обязательные формулы

### 8.1 Идентичность и написание ноты

Высота и отображаемое имя разделены:

```text
pitch_class(midi) = ((midi % 12) + 12) % 12
octave(midi) = floor(midi / 12) - 1
midi(string, fret) = tuning.open_string_midi[string] + fret
frequency(midi) = 440.0 * 2 ^ ((midi - 69) / 12.0)
```

Например, при стандартном строе:

- низкая открытая E: MIDI 40, E2;
- высокая открытая E: MIDI 64, E4;
- высокая E на 5-м ладу: MIDI 69, A4, 440 Hz;
- низкая E на 12-м ладу: MIDI 52, E3.

`C#` и `Db` имеют один pitch class, но выбираются `NoteSpelling` на основании
тоники, типа гаммы и пользовательской настройки. Не вычислять MIDI обратно из
текстовой подписи.

### 8.2 Обязательный каталог интервалов

| ID | Название | Интервалы в полутонах | Ступени |
| --- | --- | --- | --- |
| `major_pentatonic` | Мажорная пентатоника | 0, 2, 4, 7, 9 | 1, 2, 3, 5, 6 |
| `minor_pentatonic` | Минорная пентатоника | 0, 3, 5, 7, 10 | 1, b3, 4, 5, b7 |
| `major` / `ionian` | Мажор / ионийский | 0, 2, 4, 5, 7, 9, 11 | 1, 2, 3, 4, 5, 6, 7 |
| `natural_minor` / `aeolian` | Натуральный минор / эолийский | 0, 2, 3, 5, 7, 8, 10 | 1, 2, b3, 4, 5, b6, b7 |
| `harmonic_minor` | Гармонический минор | 0, 2, 3, 5, 7, 8, 11 | 1, 2, b3, 4, 5, b6, 7 |
| `melodic_minor` | Мелодический минор, восходящая форма | 0, 2, 3, 5, 7, 9, 11 | 1, 2, b3, 4, 5, 6, 7 |
| `minor_blues` | Минорная блюзовая | 0, 3, 5, 6, 7, 10 | 1, b3, 4, b5, 5, b7 |
| `dorian` | Дорийский | 0, 2, 3, 5, 7, 9, 10 | 1, 2, b3, 4, 5, 6, b7 |
| `phrygian` | Фригийский | 0, 1, 3, 5, 7, 8, 10 | 1, b2, b3, 4, 5, b6, b7 |
| `lydian` | Лидийский | 0, 2, 4, 6, 7, 9, 11 | 1, 2, 3, #4, 5, 6, 7 |
| `mixolydian` | Миксолидийский | 0, 2, 4, 5, 7, 9, 10 | 1, 2, 3, 4, 5, 6, b7 |
| `locrian` | Локрийский | 0, 1, 3, 5, 6, 8, 10 | 1, b2, b3, 4, b5, b6, b7 |

`major` и `ionian`, как и `natural_minor` и `aeolian`, могут ссылаться на одну
формулу, но иметь разные алиасы/категории без дублирования интервалов.
Мелодический минор в MVP означает современную восходящую форму в обоих
направлениях проигрывания; классический нисходящий вариант можно добавить
позже как явную политику, не скрытую специальную ветку.

### 8.3 Принадлежность гамме

Позиция видима, если:

```text
interval = posmod(position.pitch_class - tonic_pitch_class, 12)
scale.intervals contains interval
```

Смена тоники транспонирует одну формулу. Для каждой гаммы запрещено хранить 12
готовых копий нот.

## 9. CAGED-модель

### 9.1 Семантика

CAGED в MVP — не пять произвольных окон по четыре-пять ладов. Каждая форма
описывает связь переносимой аккордовой формы C/A/G/E/D с корнями, терциями,
квинтами и окружающими ступенями выбранной гаммы.

Форма должна быть декларативной и содержать:

- `id`: `C`, `A`, `G`, `E` или `D`;
- совместимые семейства строёв или признак `standard_tuning_relative`;
- один или несколько корневых якорей;
- относительные координаты `string_offset + fret_offset`;
- ожидаемую интервальную/аккордовую роль каждой опорной точки;
- диапазон визуальной области и правила октавного повторения;
- опциональную рекомендуемую аппликатуру;
- связи `previous_shape` / `next_shape` и зоны перекрытия.

Абсолютный лад вычисляется от выбранного корневого якоря. Данные формы не
должны включать конкретную тональность. Для стандартного строя маппер обязан
транспонировать формы во все 12 тоник и повторять их через 12 ладов.

### 9.2 Отображение

- Корни заметнее остальных нот и не кодируются только цветом.
- Пользователь может показать все ступени формы, только аккордовые тона,
  только корни либо подсказки аппликатуры.
- Граница формы не скрывает её перекрытие с соседней формой.
- Выбранная форма не меняет MIDI одной и той же позиции.
- Если текущий строй не поддержан данными формы, UI показывает «CAGED для
  этого строя пока недоступен» и предлагает весь гриф/позиции.

### 9.3 Проверяемые инварианты

- 12 тоник × 5 форм дают валидные позиции в пределах 0…`fret_count`.
- Транспозиция на 12 полутонов сохраняет pitch class и увеличивает MIDI на 12.
- Каждая форма содержит как минимум один корень и корректные аккордовые тона.
- Одна пара `string_index + fret` имеет один MIDI во всех представлениях.
- Последовательность форм и перекрытия не обрываются на 12-м ладу.

## 10. Позиции и боксы

Позиции гаммы — отдельные декларативные данные, а не переименованные формы
CAGED. Определение позиции может задавать:

- семейство гамм или конкретный `scale_id`;
- относительный лад якоря;
- допустимый диапазон ладов на каждой струне;
- корневые точки;
- рекомендуемые пальцы;
- связь с соседними позициями.

Для пентатоник MVP должен включать традиционные пять боксов и корректно
транспонировать их по тонике. Для семиступенных гамм допускаются 3NPS или иная
последовательная система, но она должна быть явно названа в данных и UI.
«Позиция 1» без указания системы не должна смешивать несовместимые схемы.

## 11. Алгоритмы грифа и визуализации

### 11.1 Построение модели

1. Проверить `Tuning`, `fret_count`, тонику и `ScaleDefinition`.
2. Для каждой доменной струны и каждого лада 0…`fret_count` создать
   `FretPosition`.
3. Рассчитать MIDI, pitch class, октаву и интервал от тоники.
4. Оставить позиции гаммы либо пометить остальные как скрытые.
5. Добавить роли выбранной позиции/CAGED без изменения базовой высоты.
6. Применить `NoteSpelling` только при создании отображаемой подписи.
7. Передать UI неизменяемую или неразделяемую между владельцами view-model.

Результат кэшируется по ключу из строя, числа ладов, тоники, гаммы, режима
области, выбранной формы/позиции и параметров написания. Размер окна влияет на
геометрию, но не на музыкальный состав.

### 11.2 Геометрия и hit-testing

Рисование и hit-testing обязаны использовать один `FretboardGeometry`.

- Учебный вид может иметь равномерные лады.
- Физический вид с убыванием ширины по правилу двенадцатого корня из двух —
  отдельная будущая политика.
- Визуальный порядок струн может быть обращён или зеркален без изменения
  `string_index` доменной модели.
- Каждая зона возвращает точную пару `string_index + fret`.
- При move между нотами политика retrigger/glissando задаётся явно.
- Scroll/zoom, если добавлены, преобразуют координаты до hit-test тем же
  transform, которым нарисован гриф.

### 11.3 Режимы подписей

- **Ноты**: имя с учётом enharmonic spelling; октава доступна в карточке.
- **Ступени**: интервальная ступень относительно текущей тоники.
- **Оба**: обе подписи читаемы и не сливаются в неоднозначную строку.

Смена режима не перестраивает MIDI и не перезапускает активные голоса.

## 12. Аудио-архитектура

### 12.1 Контракт

UI передаёт аудиосистеме `midi_note`, velocity/громкость и владельца контакта.
Аудиосистема возвращает непрозрачный `voice_handle`. Остановка выполняется по
handle, а не по имени ноты.

Минимальный интерфейс:

```text
note_on(midi_note, velocity, owner_id) -> voice_handle
note_off(voice_handle)
all_notes_off(reason)
set_master_volume(value)
get_active_voice_count() -> int
```

### 12.2 Реализация MVP

Перед окончательным выбором сделать короткий сравнительный прототип:

1. `AudioStreamPolyphonic`;
2. пул `AudioStreamPlayer`/голосов с синтезом или samples.

Выбор зафиксировать в `PROGRESS_ASTRA.md` с результатами Windows и Android,
если устройство доступно. Предпочтение отдаётся меньшей задержке, надёжному
release и предсказуемому управлению голосами, а не сложности решения.

Допустимы:

- простой plucked-string/синтез для полностью автономного MVP;
- sample-bank с ближайшим исходным sample и ограниченным pitch shift.

Не допускается один `AudioStreamPlayer`, перестраиваемый на последнюю ноту.

### 12.3 Голоса

- Пул: не менее 12 голосов, пользовательская полифония MVP — не менее 6.
- Каждый голос имеет attack и короткий release против щелчков.
- Voice stealing: сначала завершившийся/затухающий, затем самый старый голос,
  который не принадлежит свежему активному touch; политика детерминирована и
  тестируема.
- Два контакта на одной позиции по умолчанию получают отдельные голоса. Если
  будет выбран shared voice, нужен reference count и отдельный тест.
- Ограничить master gain/добавить безопасное суммирование, чтобы аккорд не
  клиппировал.
- При потере фокуса, паузе, уходе в фон, смене сцены и завершении дерева —
  `all_notes_off`.

Headless-тест подтверждает расчёты и lifecycle, но не доказывает слышимость,
тембр, отсутствие клиппинга или реальную задержку.

## 13. Multitouch

`TouchVoiceCoordinator` хранит независимое состояние:

```text
touch_id -> {
  position: FretPosition,
  voice_handle: Variant,
  pressed_at_ms: int
}
```

Обработка:

- `InputEventScreenTouch.pressed`: hit-test; если позиция активна, подсветить и
  вызвать `note_on`;
- повторный press существующего `touch_id`: сначала безопасно завершить старый
  голос;
- `InputEventScreenDrag`: при переходе в другую зону применить явно выбранную
  политику retrigger; в пределах одной зоны ничего не перезапускать;
- release: остановить только handle этого `touch_id` и убрать его подсветку;
- cancel/focus lost/tree exit: очистить все контакты и голоса;
- событие вне активной ноты не должно останавливать чужие контакты.

Mouse input использует отдельный owner id и не подменяет реальную проверку
нескольких `touch_id`. Настройки Godot не должны автоматически преобразовывать
touch в mouse и создавать двойное воспроизведение; текущие параметры проекта с
обеими эмуляциями `false` следует сохранить, пока адаптеры обрабатываются явно.

## 14. Расширяемость после MVP

Архитектура должна позволить добавить:

- `ChordDefinition` как интервальную формулу и CAGED chord-tone overlay;
- `ArpeggioDefinition` с порядком проигрывания без изменения `Pitch`;
- sequencer прослушивания гаммы вверх/вниз;
- тренажёры поиска нот, ступеней, интервалов и позиций;
- генератор заданий, принимающий каталог и фильтры сложности;
- локальный `PracticeSession` и агрегированную статистику;
- миграции версии сохранённых данных;
- дополнительные строи, 7/8-струнные инструменты и другое число ладов;
- бас/укулеле как новые профили инструмента при сохранении доменной модели.

Тренажёр не должен читать UI-ноды для проверки ответа. Он получает доменные
позиции и публикует результат через сервис приложения.

## 15. Coding conventions

- GDScript в стиле существующего проекта и Godot 4.x.
- Статическая типизация для публичных полей, параметров и возвращаемых значений,
  где тип не мешает работе Godot API.
- `class_name` только для устойчивых доменных/сервисных типов; избегать
  глобального пространства имён для одноразовых UI-скриптов.
- Один основной класс/ответственность на файл.
- `snake_case` для файлов, методов и переменных; `PascalCase` для классов;
  `UPPER_SNAKE_CASE` для констант.
- Сигналы описывают произошедшее событие или намерение, а не скрытый вызов
  конкретного узла.
- Не размещать интервальные таблицы, строй, CAGED и позиции в `_draw()` или
  обработчиках ввода.
- Не вычислять музыкальную истину из текста UI, цвета, визуального индекса
  струны или координат экрана.
- Не использовать магические MIDI-числа вне данных, тестовых fixtures и ясно
  названных стандартов вроде A4=69.
- Loader и validator отделены; ошибка данных не должна приводить к частично
  заполненному каталогу.
- Комментарии объясняют причину/инвариант, а не повторяют строку кода.
- Не добавлять зависимости, addon или локальный MCP без реальной необходимости
  и согласования с существующими `AGENTS.md`.
- Не инициализировать Git без прямой просьбы пользователя.

## 17. Acceptance criteria

### 17.1 Музыкальная корректность

- [ ] Стандартный строй равен MIDI `[40, 45, 50, 55, 59, 64]` от низкой E к
      высокой E.
- [ ] Для каждой струны и лада выполняется `open_midi + fret`.
- [ ] E2, E3, E4, A4 и переходы B/C вычисляются корректно.
- [ ] Смена тоники для одной формулы даёт транспозицию без копирования данных.
- [ ] Все обязательные гаммы и лады совпадают с формулами раздела 8.
- [ ] Enharmonic spelling не меняет pitch class/MIDI.
- [ ] Альтернативный строй меняет высоты без изменений в UI-алгоритмах.

### 17.2 Гриф и UX

- [ ] Все входящие ноты показаны на ладах 0…24; невходящие не помечены как
      входящие.
- [ ] Ноты/Ступени/Оба меняют только представление.
- [ ] Тоника различима цветом и вторым визуальным признаком.
- [ ] Hit-test возвращает ту позицию, которая нарисована.
- [ ] Изменение размера окна не рассинхронизирует touch zones.
- [ ] Контрольные desktop/tablet/mobile размеры остаются функциональными.
- [ ] Все основные функции доступны без клавиатуры.

### 17.3 Позиции и CAGED

- [ ] Пять минорных и мажорных пентатонических боксов транспонируются во все
      12 тоник.
- [ ] Пять форм CAGED основаны на относительных данных, а не фиксированных
      диапазонах ладов.
- [ ] Формы корректно повторяются через 12-й лад и показывают перекрытия.
- [ ] Аккордовые тона и корни соответствуют выбранной форме.
- [ ] MIDI позиции не меняется между Весь гриф/Позиции/CAGED.
- [ ] Неподдерживаемый строй не показывает заведомо неверный CAGED.

### 17.4 Аудио и ввод

- [ ] Нажатие позиции воспроизводит её MIDI-высоту, включая правильную октаву.
- [ ] A4 даёт целевую частоту 440 Hz в синтезе или эквивалентный sample pitch.
- [ ] Шесть независимых контактов звучат одновременно.
- [ ] Release одного контакта не останавливает остальные.
- [ ] Drag не создаёт дубликат голоса в пределах одной позиции.
- [ ] Voice stealing соответствует документированной политике.
- [ ] Focus lost, background, scene change и exit выполняют all-notes-off.
- [ ] Нет двойного note-on от одного физического touch из-за mouse emulation.

### 17.5 Данные и расширяемость

- [ ] Каталог гамм и ладов не зашит в UI/GDScript-ветвления.
- [ ] Невалидные интервалы, дубли, отсутствие 0 и повторный `id` отклоняются.
- [ ] Добавление валидной гаммы в data file делает её доступной без правки UI.
- [ ] Доменные сервисы не зависят от Control/Node-представления.
- [ ] Есть ясные extension points для chord/arpeggio/trainer/statistics.

## 18. Тест-план

### 18.1 Автоматические доменные тесты

- MIDI/pitch class/octave на границах октав и для отрицательных входов, если
  тип допускает их до валидации.
- Все 12 pitch classes и политика sharp/flat.
- Стандартный, Drop D, произвольный 7-струнный строй.
- Все каталожные формулы и транспозиции во все 12 тоник.
- Loader/validator: валидные и намеренно повреждённые fixtures.
- Инвариант: позиции одного pitch class повторяются через 12 ладов.

### 18.2 CAGED и позиции

- Golden cases для известных корней каждой формы.
- Матрица 12 тоник × 5 CAGED-форм.
- Матрица 12 тоник × 5 пентатонических боксов.
- Границы ладов 0 и 24, октавное повторение и overlap.
- Поведение при несовместимом/нестандартном строе.

### 18.3 Геометрия и UI

- Round-trip: центр каждой нарисованной позиции → hit-test → та же позиция.
- Точки между зонами, за границей грифа, на открытых струнах и крайних ладах.
- Resize на всех контрольных размерах.
- Scene tests сигналов селекторов и сохранения состояния.
- Скриншоты ключевых состояний: full fretboard, position, каждая CAGED-форма,
  Ноты/Ступени/Оба, phone/tablet/desktop.

Headless renderer не является окончательным доказательством внешнего вида;
нужна видимая проверка редактором/runtime или screenshot через bridge.

### 18.4 Ввод и аудио

- Synthetic touch ids: press, move внутри зоны, move в новую, release, cancel.
- 2, 6 и 12 одновременных владельцев.
- Два владельца одной позиции.
- Исчерпание пула и детерминированное stealing.
- Потеря фокуса/фон/смена сцены с активными голосами.
- Проверка расчёта частоты с допустимой числовой погрешностью.
- Ручная проверка: слышимая высота, щелчки, clipping и latency.

### 18.5 Платформенная матрица

- Windows desktop: editor, debug run, resize, mouse, keyboard, audio.
- Android phone: landscape, safe area, 6-touch при поддержке устройства,
  динамик/наушники, background/return, latency.
- Android tablet: layout, multitouch и масштаб.
- iOS: только если доступны toolchain и устройство; отсутствие проверки нужно
  явно указать, а не считать пройденной по аналогии.

## 20. Ограничения и риски

- Одновременные touch-события зависят от устройства и ОС; desktop-мышь их не
  доказывает.
- Аудиозадержка и доступный размер буфера различаются на Windows/Android/iOS.
- Sample-based звук требует лицензий, размера поставки и контроля pitch-shift;
  синтез проще юридически, но может звучать менее реалистично.
- Слишком плотный 24-ладовый гриф на узком телефоне потребует scroll/zoom или
  адаптивных hit areas.
- CAGED тесно связан со стандартным гитарным строем. Обобщение на произвольный
  строй не должно жертвовать корректностью.
- Enharmonic spelling зависит от теоретического контекста; простой
  «все диезы/все бемоли» допустим как fallback, но не как окончательная модель.
- Текущий прототип содержит жёстко заданные A minor pentatonic и визуальные
  диапазоны CAGED в UI. Это технический долг каркаса, а не эталон алгоритма.
- `godot_ai_bridge` и глобальный MCP уже настроены; дублирование локальной MCP
  конфигурации создаст конфликт маршрутизации.

   риске ошибки и должно быть отмечено в progress-файле.
2. Полностью прочитать применимые `AGENTS.md`, эту спецификацию,
   `docs/DEVELOPMENT_PLAN.md`, `README.md` и актуальное дерево проекта.
3. Проанализировать существующие сцены, скрипты, данные, tests, Godot settings
   и уже подключённый bridge. Не считать проект пустым.
4. Проверить исходный проект через Godot CLI и записать baseline.
5. Составить внутренний рабочий план по этапам с узкими критериями приёмки.
   Записывать решения и checklist, но не раскрывать и не требовать скрытую
   цепочку рассуждений.

### 21.2 Progress-файл

В начале реализации создать в корне `PROGRESS_ASTRA.md` и поддерживать его как
краткий журнал состояния. Формат:

```markdown
# FretFormula implementation progress

## Baseline
- Date/time:
- Existing state:
- Checks and results:

## Current stage
- Stage:
- Goal:
- Acceptance criteria:

## Completed
- [x] Change — evidence/check

## Next
- [ ] Next bounded change

## Decisions
- Decision, reason, affected files

## Verification gaps
- Visible/audio/device checks not yet performed
```

Обновлять файл после завершения этапа, смены архитектурного решения, найденного
ограничения или проверки. Не превращать его в лог каждого вызова инструмента.
Не отмечать пункт выполненным без проверяемого результата.

### 21.3 Правила реализации

- Реализовывать последовательно по разделу 16; сначала доменная корректность и
  data-driven каталог, затем UI/CAGED, затем audio/multitouch.
- После анализа можно уточнить файловую структуру, но нельзя менять продуктовые
  требования без подтверждённой причины.
- Если требование технически конфликтует с Godot/платформой, записать факт,
  доказательство, минимальный вариант решения и влияние в progress-файл.
- Не подменять CAGED фиксированными окнами ладов и не оставлять гаммы в UI.
- Сохранять работающие части существующего проекта и делать минимальные
  связные изменения; не проводить несвязанный рефакторинг.
- Не устанавливать новый локальный MCP: использовать глобальный workspace MCP
  и перед записью подтвердить активный проект Guitar.
- Не добавлять addon/dependency без необходимости. Если зависимость нужна,
  зафиксировать назначение, версию, лицензию и альтернативы.
- Не инициализировать Git, не публиковать и не выполнять внешние действия без
  прямого запроса пользователя.
- Использовать субагентов для подходящих простых операций согласно разделу
  21.5. Основной агент отвечает за декомпозицию, интеграцию, итоговую проверку
  и все решения, меняющие архитектуру или продуктовые требования.

### 21.4 Проверки и отчётность

- После каждого значимого изменения запускать Godot CLI import/parse и
  релевантные узкие tests.
- После изменения сцен выполнять main-scene smoke test.
- После изменения геометрии выполнять hit-test round-trip и видимую проверку.
- После изменения audio/touch выполнять lifecycle/voice tests и, когда
  возможно, реальную проверку на устройстве.
- При падении сначала установить причину; не маскировать ошибку отключением
  теста или ослаблением критерия.
- Перед завершением каждого этапа осмотреть итоговый diff и исключить
  посторонние изменения.
- В пользовательском отчёте перечислять реализованное, команды/проверки и их
  результат, непроверенные аспекты и следующий этап.

### 21.5 Субагенты и минимально достаточная модель

При разработке приложения основной агент **обязан** передавать субагентам
простые, ограниченные и независимо проверяемые операции, если их можно
выполнить без потери целостного контекста. Делегирование не является поводом
создавать лишние параллельные задачи: один субагент получает один конкретный
результат, узкую область файлов и явную проверку готовности.

Обязательная маршрутизация от самой дешёвой подходящей конфигурации:

| Уровень задачи | Модель субагента | Reasoning | Типичные операции |
| --- | --- | --- | --- |
| Механическая | `gpt-5.6-luna` | `low` | поиск/извлечение фактов, форматирование данных, переименование, простая документация, однотипные fixtures, проверка списка файлов |
| Обычная ограниченная | `gpt-5.6-terra` | `medium` | небольшой GDScript-компонент по готовому контракту, целевые тесты, локальный рефакторинг, проверка сцены или data loader |
| Сложная ограниченная | `gpt-5.6-sol` | `high` | независимый анализ аудиоконкурентности, нетривиальная диагностика, рискованный алгоритм после того, как Luna/Terra объективно недостаточны |

Правила выбора и экономии токенов:

- Начинать с `gpt-5.6-luna`/`low` для простой операции. Переходить на Terra
  только если задача требует понимания нескольких связанных файлов или
  реализации с тестами; на Sol — только по фактической сложности/риску.
- Не использовать Astra как субагента для простой или обычной операции.
- Не повышать модель «на всякий случай» и не запускать нескольких субагентов
  для одного и того же исследования.
- Передавать только необходимый контекст: цель, точные файлы/границы владения,
  ограничения `AGENTS.md`, acceptance check и требуемый краткий результат.
- Просить выводить выводы, изменённые файлы и результаты проверок, а не полный
  журнал рассуждений или длинные стенограммы команд.
- Параллелить только действительно независимые области без пересечения файлов.
  Субагентам явно сообщать, что они не одни в проекте, не должны откатывать
  чужие изменения и обязаны учитывать уже появившиеся правки.
- Не делегировать простой шаг, если постановка и интеграция заведомо дороже его
  немедленного выполнения основным агентом. В таком случае записать его как
  часть текущего связного change set; требование использовать субагентов
  считается выполненным другими подходящими простыми операциями этапа.
- Не отдавать субагенту окончательный выбор архитектуры, изменение требований,
  публикацию, удаление данных или иное последствие, требующее ответственности
  основного агента либо отдельного разрешения пользователя.
- Основной агент обязан проверить diff/результат каждого субагента, устранить
  конфликты, запустить интеграционные проверки и не считать сообщение
  субагента самостоятельным доказательством готовности.
- Если доступный интерфейс не позволяет задать модель/режим субагента, выбрать
  ближайший установленный профиль минимальной достаточной мощности и отметить
  фактическую конфигурацию в `PROGRESS_ASTRA.md`.

Примеры подходящего делегирования по этапам:

- Luna: сверить JSON-каталог с таблицей формул; подготовить однотипные fixtures;
  проверить полноту локализационных ключей; обновить краткую документацию.
- Terra: реализовать изолированный validator по готовой схеме; написать
  table-driven tests для уже определённого API; проверить responsive-сцену на
  заданной матрице размеров.
- Sol: отдельно исследовать voice stealing или Android audio lifecycle, только
  когда это действительно сложный ограниченный вопрос и результат можно
  интегрировать через заранее заданный контракт.

В `PROGRESS_ASTRA.md` для каждого делегированного результата кратко указывать:
задачу, модель/reasoning, область файлов, результат проверки и решение
основного агента о принятии или доработке.

### 21.6 Основания для отклонения от спецификации

Допустимы только:

- подтверждённое ограничение Godot или целевой платформы;
- обнаруженный конфликт с более приоритетным `AGENTS.md`;
- доказанная музыкальная ошибка в формуле/критерии;
- сохранение совместимости с уже работающей архитектурой при полном выполнении
  поведения;
- прямое изменение требования пользователем.

Каждое отклонение фиксируется в `PROGRESS_ASTRA.md`: исходное требование,
причина, выбранная замена и проверка эквивалентности. Удобство реализации или
желание переписать проект не являются причиной.

## 22. Definition of Done

MVP готов только когда одновременно выполнено следующее:

- все обязательные функции раздела 2 реализованы как рабочее поведение;
- все acceptance criteria раздела 17 выполнены либо явно согласованы как
  исключения пользователем;
- интервалы, строи, позиции и CAGED вынесены из UI-кода в валидируемые данные;
- точная высота по струне/ладу подтверждена автоматическими тестами;
- режимы Ноты/Ступени/Оба и тоника работают на всём грифе;
- CAGED и позиции являются музыкальными моделями, а не визуальными заглушками;
- полифония и независимый lifecycle контактов подтверждены тестами;
- реальный multitouch и слышимое audio проверены хотя бы на одном целевом
  mobile-устройстве; если устройства объективно нет, MVP может считаться лишь
  desktop candidate, а не mobile Done;
- адаптивность проверена на контрольных размерах и видимым runtime;
- Godot CLI import/parse, доменные/сценовые tests и smoke test проходят;
- нет известных parse/runtime errors, зависших нот и критических ошибок данных;
- ограничения, лицензии assets/samples и platform verification gaps
  документированы;
- `README.md`, `docs/DEVELOPMENT_PLAN.md` при необходимости и
  `PROGRESS_ASTRA.md` соответствуют фактическому состоянию;
- итоговый diff не содержит несвязанных изменений;
- сохранены расширяемые границы для аккордов, арпеджио, тренажёра и статистики.

Если нет реального доказательства audio, multitouch или mobile lifecycle,
нужно прямо назвать соответствующую часть непроверенной. Успешный headless
запуск не заменяет эти критерии.
